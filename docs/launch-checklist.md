## Что требуется для постоянного запуска

Бот, токен и ID тестового администратора уже настроены. Остаются:

- Постоянный публичный HTTPS-адрес и место размещения приложения/PostgreSQL.
- Рабочие названия брендов, типов, товары и цены; демонстрационный набор не
  переносится в рабочую базу автоматически.

## Настройка и запуск

1. Настроить рабочую `ConnectionStrings:Shop` и явно применить миграции
   по командам README. Не применять их к локальной демобазе вместо рабочей.
2. Опубликовать приложение вместе с frontend. При HTTPS на Kestrel дополнительные
   прокси-заголовки не нужны. При завершении TLS на прокси настроить
   `ReverseProxy:KnownProxy` (или `ReverseProxy__KnownProxy`) на его точный IP,
   видимый приложению. Прокси должен перезаписывать X-Forwarded-Proto протоколом
   исходного соединения; доступ к внутреннему HTTP-порту ограничить этим прокси.
   В Compose переменная — `TRUSTED_PROXY_IP`. Доверие ко всем адресам не включать.
3. Сначала проверить HTTPS-каталог и `/api/health/ready` (200).
4. Назначить первого администратора локальной командой из README `--grant-admin`.
   Она использует рабочее подключение и не запускает HTTP/бота.
5. Указать `Telegram:MiniAppUrl`, токен и `Telegram:Enabled=true`. Перед polling
   проверить, не используется ли webhook/тот же токен другим экземпляром.
   Существующий webhook отключать только при осознанном переключении.
6. Запустить один экземпляр приложения с polling. Указать URL Mini App в BotFather
   для меню/профиля при необходимости; кнопка в ответе `/start` уже реализована.

## Настоящая приёмка в Telegram

Открыть `/start` в личном чате и магазин по кнопке. Обычный пользователь видит
каталог, фильтры, цену и варианты; прямые административные запросы ему запрещены.
Администратор создаёт бренд/тип, товар с двумя вариантами, публикует, меняет цену
и скрывает вариант. Клиент после обновления видит актуальный результат.
Проверить светлую/тёмную темы, мобильные отступы, BackButton, потерю сети,
истечение входа и сохранность данных после перезапуска приложения.

F06 завершается только после записи результатов этой проверки и фактического
размещения. Контейнерную сборку проверить при доступном Docker engine.

## Локальная сквозная проверка

Сначала выполнить `scripts/publish.ps1 -OutputDirectory artifacts/mvp-publish`.
Затем `scripts/test-e2e.ps1`: требуется установленный PostgreSQL 18, Edge и
Node.js с Playwright (путь к модулю задаётся `PLAYWRIGHT_MODULE`, если он не
установлен в обычном поиске Node). Параметр `-NodeExecutable` задаёт путь к Node.
Тест сам создаёт изолированный кластер и случайный тестовый токен; рабочие
настройки не используются. По умолчанию процессы останавливаются в finally.
`-Port 8081 -KeepRunning` оставляет демонстрацию после успешной проверки.
Остановка — `scripts/stop-local-preview.ps1`. Пароль/токен не печатаются;
временный файл пароля удаляется, файлы остановленного кластера сохраняются.
