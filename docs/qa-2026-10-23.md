### Коды обращений и последовательности

- **cfdc5109**, operation_not_found: GET уточнения после отказов создания;
  рядом транспортный отказ уточнения **c0063b5f**. Далее создание проходит
  (**40187284**). По diagnostics.md это предусмотренный ответ, не исчезновение
  существующего товара. Без ключей в логе принадлежность запросов одному
  намерению предполагается по последовательности, а не доказывается.
- **c8a8255d**, validation_failed: PUT редактирования. Далее есть транспортный
  отказ PUT **60702491** и успешный PUT **c4ff9d7b**. Без тела ответа или
  сообщения владельца нельзя определить поле и причину отклонения.
- Примеры транспортных отказов: вход **dbab7d11**, создание **685362e0**,
  изменение **21b2158d**, справочник **810be25d**.

Все эти ответы имеют requestId, который интерфейс умеет сокращать до «Кода
обращения». Серверный журнал не доказывает показ каждого ответа пользователю:
повторы могут его скрыть. В форме operation_not_found преобразуется в пояснение
о возможности сохранить повторно; это не обязательно показ самого кода обращения.

В журнале два успешных save/201: создание **типа** (9308e884) и **товара**
(40187284). Сумму всех 201 нельзя сравнивать с числом товаров. Три успешных PUT:
eb4f9ab7, c4ff9d7b, 9cda5df8.

В БД три товара, все видимы в каталоге: два созданы 15 октября, один — сегодня
в **17:46:48**. В save_operations одна сегодняшняя product.create для товара 3
и три product.update для товара 1. Групп с одинаковыми нормализованным названием,
брендом и типом нет. Данные согласуются с одним новым товаром, признаков дубля нет.
Это не доказательство отсутствия любых возможных дублей по одной только сумме HTTP.
Отпечаток товаров, вариантов и справочников до/после проверки одинаковый:
`2b5b173e508d7b183c454c49affa8dcd`.

### HTTPS, туннель и исключения

Все 68 предупреждений содержат `Loopback: True; forwarded protocol header:
False; original protocol header: True`. Это **признаки наличия**, не значения
заголовков. Схема не записана; из ветки кода известно только Request.IsHttps=false.
UseForwardedHeaders выполняется раньше проверки и может потребить заголовок:
его отсутствие на этом этапе не доказывает, что туннель не передал его.
Значения http/https восстановить нельзя. В проверявшемся исходнике c71feb4
формат тоже старый. При последующей сверке GitHub найден уже влитый PR #21:
он добавляет безопасные значения схемы и заголовков. В изученном рабочем логе
по-прежнему bool; новых значений в этом срезе нет. Публикация не обновлялась.

request failed (RequestException); retrying in 5 seconds`, без времени/стека:
оно относится к Bot API и не доказывает ошибку сохранения товара.

## Подтверждённые проблемы и предлагаемые задачи

**QA01 / P0 — нестабильное подтверждение HTTPS.** Вход/управление/сохранение через
текущий туннель периодически дают 503, затем проходят. Сам запрет корректен.
Следующий шаг: безопасная диагностика значений протокола и времени; сопоставление
с туннелем. Не отключать HTTPS и не доверять произвольным заголовкам.
Постоянное размещение R08 остаётся отложенным владельцем.

**QA02 / P1 — журнал не позволяет восстановить время и протокол.** Воспроизведение:
найти любой requestId и попытаться определить время/значения заголовков. Места:
Program.cs, TelegramAuthenticationHandler.cs. Предложение: UTC-время с зоной,
Request.Scheme и ограниченные нормализованные значения протокольных заголовков,
без IP, токена, initData и тела формы.
Значения протокола уже добавлены Claude в main через PR #21 — эту часть повторно
не реализовывать. Остаются временные метки и проверка расширенного журнала после
обновления публикации в согласованное окно; сейчас рабочий процесс не трогать.

**QA03 / P1 — ложный SKIP резервирования на Windows.** Воспроизведение: test-all
при установленном C:\Program Files\PostgreSQL\18\bin и отдельной тестовой БД.
run() в scripts/test-all.cjs включает shell=true и передаёт путь pg_dump без
экранирования. Предложение: .exe запускать без shell, .cmd обрабатывать отдельно;
проверить Windows-путь с пробелами. Это дефект запуска тестов, не рабочей БД.

**QA04 / P1 — кодировка SQL-фикстуры.** Прямой backup-тест без PGCLIENTENCODING
на этой Windows падает на кириллице в аргументе psql -c (стек sql:23 → строка 38).
Явная WIN1251 позволяет пройти тест. Предложение: SQL через stdin UTF-8 и
согласованный client_encoding вместо кириллицы в аргументе; проверки Unicode
на Windows/Linux. Настройку WIN1251 не считать универсальным исправлением.

Один отказ валидации — не установленный дефект: нужно сообщение владельца
с полем и кодом обращения. Тайм-аут ссылки — наблюдение доступности среды,
связь с VPN не доказана. Исправления QA01–QA04 в этом PR не реализованы.

## Что остаётся для настоящего Telegram

Вход обоих администраторов, возврат из фона, черновик после закрытия WebView,
смена сети/VPN, клавиатура и safe area Android/iOS, экранный диктор, крупный
системный шрифт, скорость на телефоне. Полный E2E с перезапусками опубликованного
приложения намеренно не выполнялся. Сведения владельца внесены в
[device-protocol.md](device-protocol.md) с источником и неизвестными полями.
