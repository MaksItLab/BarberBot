# Анализ группы «Устойчивая эксплуатация» без хостинга: R09, R10

Дата: 23 октября 2026. Роли: аналитик и разработчик (один ассистент, отдельные проходы).
Группа 3 из [backlog.md](backlog.md#порядок-поставки): R09 → R08, R10. R08 (хостинг)
отложен владельцем 23.10.2026: «пока что делаем и тестируем при локальном запуске
через туннель». Поэтому здесь только части, которые не зависят от сервера.
U01, U04–U07 — следующая группа (4), их анализ — [experience-analysis.md](experience-analysis.md).

## Исходное состояние

- Приложение у Максима работает из `artifacts/local-preview.json`: опубликованная
  сборка и кластер PostgreSQL 18 в `artifacts/e2e/<run>/data`. Его создал
  `scripts/test-e2e.ps1 -KeepRunning`: свежий `initdb`, пользователь `cosmetics_e2e`,
  случайный пароль. Файл с паролем удаляется после запуска. В этой БД настоящая роль
  администратора (Telegram ID владельца) и всё, что внесено через туннель.
- Риски, найденные при анализе:
  1. **Повторный запуск `test-e2e.ps1 -KeepRunning` создаёт новую пустую БД**, а
     старая остаётся в другой папке и больше не используется. Внесённые товары
     «пропадают» для приложения, хотя файлы ещё лежат на диске.
  2. Каталог `artifacts/` исключён из Git и выглядит как временный: его легко
     удалить при уборке вместе с единственной копией данных.
  3. Пароль рабочей БД нигде не сохранён, поэтому `pg_dump` к ней сейчас не
     подключится. Копия возможна только остановкой кластера и копированием файлов.
- Резервных копий нет. CI нет: тесты запускаются вручную.
- Серверные тесты (67) и браузерные наборы (12) уже покрывают почти все сценарии
  R10, но запускаются по отдельности, а браузерные жёстко требуют Edge (`channel: 'msedge'`).

## Источники (проверены 23.10.2026)

| Источник | Что берём |
| --- | --- |
| [PostgreSQL 18: pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) | `-Fc` (сжатый архив, выборочное восстановление). Согласованный снимок без блокировки записи. Восстановление `pg_restore` в пустую БД из `template0`. `--no-owner` для восстановления без суперпользователя. pg_dump не выгружает сервер новее себя; роли не входят. После восстановления `ANALYZE`. |
| [PostgreSQL 18: Backup and Restore](https://www.postgresql.org/docs/current/backup.html) | Три способа: SQL dump, копия файлов при остановленном сервере, непрерывное архивирование WAL. Для маленькой БД каталога достаточно логической копии; WAL/PITR — избыточно до заказов. |
| S07 из backlog | Копия без проверенного восстановления не считается копией. |
| [Microsoft: schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create) | Расписание на Windows без сторонних программ: ежедневная задача от имени пользователя. |

Общих рекомендаций по регрессионному набору для Telegram Mini App не нашлось: R10
опирается на собственные наборы проекта и S01–S07.

## R09 · Резервная копия и проверенное восстановление (локально)

**Варианты для рабочей БД:**

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Постоянная локальная БД (рекомендуется).** Отдельная БД `cosmetics` в установленном PostgreSQL 18 (служба Windows, порт 5432), пароль в исключённом из Git `appsettings.Local.json`. Перенос текущих данных один раз. | Данные не зависят от `artifacts/` и от перезапуска демонстрации; `pg_dump` работает без остановки; тот же подход перейдёт на сервер в R08. | Разовый перенос с остановкой приложения на несколько минут; нужен пароль, который знает только Максим. |
| B. Оставить кластер демонстрации, копировать файлы с остановкой | Ничего не переносить. | Каждая копия останавливает магазин; данные по-прежнему в `artifacts/`; при следующем `-KeepRunning` снова пустая БД. |
| C. Оставить кластер, сохранить пароль при следующем запуске | `pg_dump` без остановки. | Текущий пароль уже утрачен: нужен новый запуск, то есть пустая БД, либо правка `pg_hba.conf` рабочего кластера. |

Решение выбирает Максим: это его рабочие данные и его компьютер.

**Процедура (для A, остальные варианты меняют только источник):**

- `scripts/backup-database.cjs` (Node: уже нужен для туннеля, работает на Windows и в
  тестовом Linux-контейнере):
  - `pg_dump -Fc --no-owner` во временный файл, затем переименование в
    `shop-YYYYMMDD-HHmmss.dump`; рядом `.json` с размером, SHA-256, версией
    PostgreSQL и последней миграцией;
  - строка подключения — из `appsettings.Local.json` или переменной окружения,
    в журнал и метаданные не пишется;
  - срок хранения: 14 ежедневных копий, старые удаляются только после успешной новой;
  - итог — `status.json` (время, успех, причина отказа) и код выхода ≠ 0 при сбое.
- `scripts/verify-backup.cjs`:
  - создаёт **отдельную временную** БД (`shop_restore_check_<run>`), восстанавливает
    последнюю копию через `pg_restore`, выполняет `ANALYZE`;
  - сравнивает с источником число строк по таблицам и контрольную сумму
    содержимого каталога (бренды, типы, товары, варианты, пользователи и роли);
  - записывает длительность восстановления, возраст копии и результат; удаляет
    временную БД. Рабочую БД только читает.
- Расписание: задача Планировщика Windows раз в сутки (команда в инструкции, ставит
  сам Максим). Обнаружение сбоя: код выхода в истории задачи и `status.json`; при
  возрасте последней успешной копии > 36 ч проверка завершается отказом (код ≠ 0);
  `GET /api/health/ready` не меняем.
  *Уточнение при реализации 23.10.2026:* вместо предупреждения — отказ, потому что
  предупреждение в Планировщике не видно, а код выхода виден в истории задачи. Оба
  скрипта объединены в `scripts/database-backup.cjs` (команды `backup` и `verify`).
- Место хранения: по умолчанию папка вне репозитория (`%LOCALAPPDATA%\BarberBot\backups`).
  Вторую копию на другом диске или в облачной папке выбирает Максим; копии содержат
  Telegram ID пользователей, поэтому не в репозиторий и не в общий доступ.
- Цели (предварительные, из backlog): потеря ≤ 24 ч, восстановление ≤ 2 ч. Фактические
  длительность, полнота и свежесть фиксируются первым проверенным восстановлением.

**Ошибки и крайние случаи:** нет `pg_dump` нужной версии (pg_dump старше сервера
отказывается) → понятная ошибка с путём; диск заполнен → временный файл удаляется,
старые копии не трогаются; БД недоступна → отказ без пустого файла; копия
повреждена → `verify-backup` падает до сравнения; параллельный запуск → файл-замок.

**Критерии приёмки R09 (локальная часть):**
1. Копия создаётся без остановки приложения и без записи пароля в журнал.
2. Восстановление в отдельную БД проходит; строки и контрольная сумма совпадают.
3. Повреждённая копия, недоступная БД и нехватка места дают отказ с кодом ≠ 0 и
   не удаляют прежние копии.
4. Зафиксированы длительность восстановления, размер и возраст копии.
5. Инструкция расписания и восстановления рабочей БД в `docs/`.

**Проверки:** автотест скриптов в контейнере PostgreSQL 18 с отдельной тестовой БД
(Node с хоста примонтирован в образ `postgres:18`): копия → восстановление →
сравнение; порча файла; недоступная БД; срок хранения; отсутствие пароля в выводе.
На компьютере Максима — первое реальное восстановление после его решения, с записью
длительности. Рабочую БД ради проверки не очищать и не менять.

## R10 · Регрессионный набор отказов и прав

**Что уже есть:** неверная подпись, срок, роль, снятие роли (`AuthHttpTests`,
`RoleRevocationHttpTests`), HTTPS за прокси (`ProxyHttpTests`), повтор без дублей и
потеря ответа (`IdempotentSaveHttpTests`), откат и перезапуск хоста
(`SaveIntegrityHttpTests`), 409 и слияние (`conflict.cjs`), 503 и обрывы
(`auth-transport.cjs`, `diagnostics.cjs`, `save-result.cjs`), черновик и
`auth_expired` (`drafts.cjs`), сворачивание (`login-lifecycle.cjs`).

**Чего не хватает:**
- одного запуска всего набора с итоговым отчётом и списком ограничений;
- запуска без Edge: браузерные файлы жёстко задают `channel: 'msedge'`;
- автоматического запуска на каждый PR (сейчас правило merge держится на дисциплине);
- протокола настоящих устройств (шаблон для R02), отдельного от эмуляции.

**План:**
1. `PLAYWRIGHT_CHANNEL` в браузерных наборах: по умолчанию `msedge` (как у Максима),
   пустое значение — встроенный Chromium. Поведение тестов не меняется.
2. `scripts/test-all.cjs`: серверные тесты, затем каждый браузерный набор; итог
   PASS/FAIL по каждому, общая длительность и раздел «Не проверено» (настоящий
   Telegram, телефон, `e2e.cjs` вне Windows).
3. GitHub Actions `.github/workflows/tests.yml` на каждый PR: PostgreSQL 18 как
   service-контейнер, .NET 10, pnpm, Vite и браузерные наборы в Chromium. Для
   публичного репозитория бесплатно; секреты не нужны (тесты используют тестовые
   токены). Если запуск в Actions окажется недоступен для репозитория, набор
   остаётся локальным, и это записывается в отчёт.
4. `docs/device-protocol.md`: таблица ручной проверки на телефоне и компьютере
   (устройство, версия Telegram, сеть/VPN, шаг, результат, код обращения R01).
   Заполняет Максим; эмуляция в нём не отмечается.

**Критерии приёмки R10:** весь набор запускается одной командой и в CI; результат
перечисляет ограничения; запрет доступа, отсутствие дублей и сохранность
подтверждённых данных проверяются в каждом запуске; протокол устройств отделён.

## Порядок реализации

1. R10 шаги 1–3 (CI сразу проверяет всё последующее).
2. R09 скрипты и автотесты — не зависят от решения по рабочей БД.
3. R09 перенос рабочей БД и первое реальное восстановление — после решения Максима.
4. R10 шаг 4 (протокол) вместе с R02, когда будет проверка на телефоне.

## Разногласия и выбранное решение

Аналитик предлагал проверять свежесть копии в `/api/health/ready`. Разработчик
против: готовность приложения не зависит от резервирования, и при старой копии
туннель-супервизор считал бы приложение неготовым. Решение: свежесть проверяет
скрипт, а health не меняется. При реализации предупреждение заменено отказом
проверки (см. уточнение выше).
