HTTP-маршруты — в Api. Прямой доступ обработчиков Api/Application к
`ShopDbContext` заменяется конкретными интерфейсами сценариев/чтения;
универсальная repository-обёртка не вводится. Требования и критерии фич сохранены.

## Общие требования

- У товара один бренд и один тип; варианты выбираются внутри карточки.
- Цена принадлежит варианту, валюта RUB. Остатков и отметок о наличии нет.
- В публичной выдаче только видимые товары с видимыми вариантами.
- Публичное чтение работает без входа; административные запросы защищены сервером.
- Ошибки API возвращаются в согласованном формате Problem Details; интерфейс
  переводит их в понятные сообщения без внутренних исключений и SQL.
- Изображения необязательны, без загрузки в стороннее хранилище.
- Записи ORM не выдаются напрямую; входные DTO ограничивают изменяемые поля.
- Тесты, ревью и исправления входят в каждую фичу, а не откладываются в F06.

## F01. Каталог и фильтры

**Аналитик: поведение и критерии.**

- Пользователь видит карточки с названием, брендом, изображением/заглушкой и ценой.
- При одинаковой цене вариантов показывается цена; при разных — «от … ₽».
- Фильтры по бренду и типу работают отдельно и совместно; есть сброс.
- Есть загрузка, пустой каталог, отсутствие результатов, ошибка и повтор.
- Загрузка следующей страницы не сбрасывает выбранные фильтры.

**Разработчик: реализуемость и решение.**

- Minimal API: `GET /api/catalog/products`, `/api/catalog/brands`, `/api/catalog/types`.
- Параметры списка: `brandId`, `typeId`, `page` (от 1), `pageSize` (по умолчанию 20, максимум 60).
- Ответ списка: `items`, `page`, `pageSize`, `hasMore`; порядок по ID товара стабилен.
- Чтение через EF Core: фильтрация и проекция в SQL, без загрузки всех товаров
  или запросов по одному варианту на каждую карточку. `hasMore` определяется
  дополнительной строкой сверх размера страницы.
- Справочники публичных фильтров включают значения, используемые хотя бы одним
  опубликованным товаром; выбранный другой фильтр не меняет набор справочника.
- Некорректные параметры дают 400, корректный неизвестный ID фильтра — пустую выдачу.
- React хранит фильтры в параметрах URL, отменяет устаревшие запросы и сохраняет
  состояние списка/позицию при переходе в товар и обратно.

**Проверки и ревью.**

Комбинации фильтров, границы страниц, скрытые товары/варианты, расчёт цены,
пустая выдача, плохие параметры, отмена запроса и повтор после ошибки.
Ревью проверяет размер выдачи, количество запросов, соответствие DTO и UI.

## F02. Карточка товара и варианты

**Аналитик: поведение и критерии.**

- Одна карточка показывает описание товара, бренд и описание бренда, тип,
  изображение/заглушку, характеристики и точную цену выбранного варианта.
- Переключение варианта меняет характеристики и цену без открытия другого товара.
- При единственном варианте лишний переключатель отсутствует.
- Возврат восстанавливает фильтры и позицию каталога.
- Для скрытого, неизвестного товара или товара без видимых вариантов показывается
  недоступность и переход в каталог.

**Разработчик: реализуемость и решение.**

- `GET /api/catalog/products/{id}` возвращает общие поля и видимые варианты.
- Неизвестный/недоступный товар возвращает 404; скрытые варианты не попадают в DTO.
- Для MVP используется один список реальных вариантов с подписями вроде
  «50 мл · оттенок 02»; выбор не создаёт несуществующих комбинаций характеристик.
- Изначально выбран самый дешёвый видимый вариант, затем по ID для равных цен.
- Описание выводится как текст. Путь изображения используется как ссылка
  на разрешённый локальный ресурс, а не как путь чтения файлов сервера.
- Кнопка Back Telegram согласуется с навигацией приложения.

**Проверки и ревью.**

404 и скрытые данные, один/несколько вариантов, равные и разные цены,
ошибка изображения, безопасный вывод текста, выбор и возврат в каталог.
Ревью проверяет, что карточка и список используют одинаковые правила видимости и цены.

## F03. Telegram-вход и роли

**Аналитик: поведение и критерии.**

- В Telegram приложение определяет пользователя и получает его серверную роль.
- Клиент не может назначить себе администратора.
- Без входа остаётся доступен публичный каталог; административный раздел закрыт.
- Администратор видит управление магазином; сервер повторно проверяет права при запросах.
- Просроченный вход обрабатывается понятным предложением заново открыть Mini App.

**Разработчик: реализуемость и решение.**

- Используется серверная схема аутентификации Telegram. Клиент передаёт
  оригинальные `initData` в заголовке `Authorization: tma …` по HTTPS.
- Проверяются подпись, корректность пользователя и время `auth_date`.
  Срок действия настраивается, исходное значение — один час; большой сдвиг
  даты в будущее отклоняется. При истечении клиент заново открывает приложение.
- Парсинг неоднозначных/повторяющихся параметров отклоняется; сравнение подписи
  выполняется за постоянное время. `initDataUnsafe` не используется как доказательство входа.
- `POST /api/auth/telegram` регистрирует нового пользователя только как Customer;
  `GET /api/me` отдаёт проверенную личность и роль. Последующие защищённые
  запросы проверяют данные Telegram и текущую роль в БД.
- Административные группы маршрутов используют политику Admin. Отсутствие или
  недействительность входа дают 401, недостаточная роль — 403.
- Первый администратор назначается отдельной локальной серверной командой по
  Telegram ID. Публичного назначения ролей и интерфейса управления администраторами в MVP нет.
- Не вводятся дополнительные JWT/refresh-токены или зависимости от cookies.
  Исходные данные входа и токен бота не попадают в журналы.

**Проверки и ревью.**

Валидные/подменённые/просроченные данные, дата в будущем, ошибки формата,
крупные Telegram ID, повторная регистрация, смена серверной роли, 401/403,
попытка прислать свою роль. Время и криптографические входные данные управляются
в тестах. Ревью отдельно проверяет обработку секретов и доступ ко всем write-маршрутам.

## F04. Управление брендами и типами

**Аналитик: поведение и критерии.**

- Администратор просматривает, добавляет и переименовывает бренды и типы.
- Для бренда доступно необязательное описание.
- Пустые имена и точные дубликаты после удаления пробелов по краям отклоняются.
- Форма сохраняет введённые значения при ошибке и показывает понятное сообщение.

**Разработчик: реализуемость и решение.**

- Группы `/api/admin/brands` и `/api/admin/types`: GET, POST и PUT по ID.
- Проверяются длины по модели, обязательные поля и уникальность; дубликат — 409,
  плохой ввод — 400, неизвестная запись — 404.
- Административные списки содержат и неиспользуемые значения.
- Связанные товары продолжают ссылаться на тот же ID после переименования.
- Удаление справочников не входит в эту фичу: БД уже запрещает удаление используемых.

**Проверки и ревью.**

Роли, создание/изменение, дубликаты, длины/пробелы, отсутствие записи,
сохранность связей и формы при ошибке. Ревью проверяет серверную валидацию и
соответствие поведения ограничениям PostgreSQL.

## F05. Управление товарами и вариантами

**Аналитик: поведение и критерии.**

- Администратор видит все товары, в том числе скрытые, создаёт и изменяет их.
- Форма содержит общие поля товара и список вариантов с ценами в рублях.
- Характеристики варианта необязательны, цена обязательна. При отсутствии
  характеристик существует единственный стандартный вариант.
- Товар/вариант можно скрыть и вернуть в каталог. Публикация требует хотя бы
  одного видимого варианта и заполненных обязательных полей.
- У скрытого черновика может не быть вариантов. Кнопки окончательного удаления
  товаров и вариантов не добавляются.

**Разработчик: реализуемость и решение.**

- `/api/admin/products`: список с ограничением размера страницы, создание,
  получение по ID и изменение агрегата товара с вариантами.
- Общие поля и варианты сохраняются одной транзакцией; частичная запись не допускается.
- Пустые характеристики нормализуются в null; дубли комбинаций дают 409.
- Цена: неотрицательное значение, не более двух знаков после запятой и в пределах
  `numeric(12,2)`. Значения не округляются молча при вводе через API.
- Бренд/тип и принадлежность изменяемых вариантов проверяются сервером.
- При скрытии последнего видимого варианта опубликованного товара нужно также
  скрыть товар; иначе возвращается ошибка, объясняющая правило.
- При конкурентном редактировании проверяется версия записи, чтобы не затереть
  чужие изменения; конфликт возвращается как 409. Версия передаётся непрозрачным
  значением; механизм EF настраивается в рамках этой фичи и проверяется интеграционно.
- Для изображения разрешён только путь к локальным ресурсам приложения;
  загрузка файлов остаётся за пределами MVP.

**Уточнение реализации перед F05.** Версия агрегата использует PostgreSQL xmin
и передаётся как непрозрачная строка. Любое сохранение вариантов также обновляет
строку товара, чтобы проверка версии защищала весь агрегат. Не более 100 вариантов
в одном товаре. Существующие варианты нельзя пропускать при сохранении —
для исключения из каталога их нужно скрывать. Изображения: локальные
`/images/…` PNG/JPEG/WebP/AVIF; пути к файловой системе и внешние URL отклоняются.

**Проверки и ревью.**

Создание/изменение, черновик/публикация/скрытие, минимальная цена после смены
видимости, неправильные ссылки, чужой вариант, дубли, точность и границы цены,
откат при ошибке, конфликт двух сохранений и запрет доступа клиенту.
Ревью проверяет атомарность, права, отсутствие массового присвоения полей и
корректность клиентского каталога после изменений.

## F06. Запуск в Telegram и приёмка MVP

**Аналитик: поведение и критерии.**

- `/start` открывает магазин с работающими каталогом и карточкой товара.
- Администратор меняет товар; после обновления клиент видит актуальные данные.
- Состояния ошибок, темы Telegram и навигация проверены на мобильном экране.
- Приложение перезапускается без потери сохранённых товаров.

**Разработчик: реализуемость и решение.**

- Используются существующие бот, Compose и совместная публикация.
- Настраиваются рабочее подключение PostgreSQL, явное применение миграций,
  токен, публичный HTTPS-адрес и первый администратор.
- Long polling запускается в одном экземпляре; существующий webhook
  отключается осознанной операцией при необходимости.
- Приёмка использует небольшой согласованный набор демонстрационных товаров;
  автоматическое заполнение рабочей базы при каждом старте не вводится.
- Для реального запуска нужны пользовательские настройки токена, размещения
  и Telegram ID администратора. Они не мешают реализации и автоматическим
  проверкам F01–F05 и не подменяются выдуманными данными.

**Проверки и ревью.**

Сборка, миграция, перезапуск, сквозной путь «администратор изменил → клиент
увидел», открытие из Telegram, светлая/тёмная темы, возврат и отказ сети.
Автоматические проверки и реальная проверка в Telegram фиксируются отдельно.
Ревью проверяет настройки размещения, секреты, готовность БД и ограничения запуска.

## Разработчик + аналитик: итог

Все шесть фич реализуемы выбранным стеком и сохраняют текущую модель из пяти
сущностей. API публичного чтения можно начать до настройки настоящего бота.
Административные write-операции зависят от F03. Вопросы размещения и реального
администратора понадобятся перед внешней приёмкой F06.

Результаты реализации фиксируются ниже; настоящий Telegram проверяется отдельно.

## F01: результат — 15 октября 2026

Реализованы публичные endpoints, проекция цен в SQL, фильтры, страницы и
интерфейс с сохранением фильтров в URL. Публичные ID передаются строками,
чтобы JavaScript не терял точность bigint; входные фильтры проверяются как long.
Схема БД не менялась. Каталог пока не заполнен рабочими товарами.

Сборка Release без предупреждений, frontend build успешен. Все 24 серверных
теста пройдены, в том числе новые проверки каталога на PostgreSQL и HTTP 400
с Problem Details. Браузерный тест `tests/frontend/catalog.cjs` проверяет
цены, фильтры/сброс, URL/перезагрузку, страницы, пустую выдачу, ошибку/повтор,
мобильную ширину и тёмную тему. API в этом браузерном тесте подменено данными;
реальный PostgreSQL проверен серверными тестами отдельно.

Саморевью: проверены границы слоёв, SQL-проекция без N+1, видимость,
границы пагинации и отмена запросов. Найдено и исправлено неоднозначное
доступное имя select-фильтров; браузерный тест после исправления пройден.
Существенных открытых замечаний нет. Восстановление списка при возврате
из карточки входит в F02, где появляется сам переход.

## F02: результат — 15 октября 2026

Добавлен endpoint подробностей с общими правилами видимости каталога,
описанием бренда и реальными вариантами, упорядоченными по цене и ID.
В интерфейсе — описание текстом, выбор варианта и цены, заглушка изображения,
недоступный товар, возврат с сохранением списка/фильтров/прокрутки и BackButton.

Все 26 серверных тестов пройдены. Frontend собран; браузерный тест дополнен
переключением вариантов/цены, единственным вариантом, безопасным текстом,
ошибкой картинки, возвратом и прокруткой, прямым открытием 404 и BackButton
с подменой Telegram SDK. Снимки экрана проверены визуально.

Отдельное саморевью проверило единые правила видимости/цены, отсутствие
выдуманных комбинаций, отмену загрузки, подписки/отписки BackButton и
переходы через историю. Существенных замечаний нет. Настоящий Telegram
и сохранение списка после полной перезагрузки страницы товара не проверялись;
состояние списка сохраняется при обычном переходе в карточку и обратно.

## F03: результат — 15 октября 2026

Реализованы HMAC-проверка initData, срок действия, строгий разбор параметров,
проверка пользователя, авторизация tma и политика Admin. Регистрация атомарна,
новый пользователь получает Customer; роль перечитывается из БД для каждого
запроса. Первый администратор назначается только локальной командой
`--grant-admin`. В production вход через незашифрованный HTTP отклоняется.
Для TLS-прокси в F06 необходимо настроить доверенную передачу протокола.

Все 42 серверных теста пройдены: независимый HMAC-вектор, подмена, возраст,

## F06: автоматическое обновление временной ссылки — анализ

Владелец выбрал остаться на localhost.run. PM и разработчик выделили два
последовательных изменения: актуальный URL в ответах бота без перезапуска и
локальный процесс сопровождения SSH, который сообщает приложению смену адреса.
Это инструменты локальной демонстрации; постоянное размещение не добавляется.

Аналитик и разработчик согласовали поведение: новый /start использует последнюю
проверенную HTTPS-ссылку. Старые сообщения автоматически не редактируются.
Смена URL не перезапускает приложение или PostgreSQL, не меняет роли/токен и
не ослабляет проверку HTTPS. Автообновление URL не доказывает стабильность
протокольных заголовков localhost.run или успешный настоящий Telegram-вход.

Реализация: отдельный необязательный appsettings.Tunnel.json только с URL,
reloadOnChange и IOptionsMonitor в worker. Переменные окружения сохраняют высший
приоритет; при локальном запуске фиксированного Telegram__MiniAppUrl быть не должно.
Node-процесс использует встроенный SSH без пользовательских ключей, включает
proxy headers, разбирает только JSON-события регистрации и допускает только
HTTPS-хосты localhost.run/lhr.life. Перед записью проверяет JSON readiness=ready;
сбой проверки сохраняет прежнюю конфигурацию. При новом событии повторяет проверку.
Не разбирает shell-команды из вывода SSH, не читает и не печатает секреты.

Приёмка: тест двух последовательных /start при смене options; тесты отказа
неподходящего домена/протокола, неверной readiness и смены URL; реальная запись
нового файла должна обновлять options работающего приложения. После этого —
саморевью, исправления и проверка каталога/входа в реальном окружении.

Дополнительный анализ входа: SDK подключается с внешнего telegram.org; его сбой
оставляет каталог доступным, но может оставить клиента в гостевом состоянии.
Официальный SDK получает исходные подписанные данные из tgWebAppData в fragment.
Разработчик добавляет чтение того же исходного значения из fragment как резервный
источник при отсутствии SDK, только в памяти страницы. Подпись/возраст/роль
по-прежнему проверяются исключительно сервером; роль из URL не используется.
В интерфейсе нужны состояние проверки входа и понятное сообщение, если Telegram
не передал данные, а также повтор входа после отказа. Проверки: SDK недоступен,
подписанные данные переданы без изменения; серверный отказ не показывает админку;
обычный браузер без данных не выполняет вход; навигация не теряет исходное значение.

## F06: нестабильный защищённый вход с телефона — анализ

Владелец подтвердил админскую кнопку на ноутбуке и периодическое появление на
телефоне с потерей доступа после перехода. Журнал подтверждает отказ проверки
HTTPS: доверенный loopback-прокси обработан, но запрос не отмечен как HTTPS.
Текущий ответ 401 ошибочно сбрасывает пользователя как при истёкшей подписи.

PM/разработчик выделили исправление серверной классификации и зависимое
восстановление клиента. Аналитик/разработчик согласовали: неподтверждённый HTTPS
в Production по-прежнему запрещает операцию, но возвращает 503 с кодом
secure_transport_unavailable. Код выдаётся до проверки подписи/роли и до
прикладной операции. Настоящие неверные данные остаются 401, запрет роли — 403.

Клиент повторяет запрос до четырёх попыток только при этом 503/коде, с короткой
задержкой и отменой через AbortSignal. Другие 503, сетевые ошибки и неопределённые
результаты записи автоматически не повторяются. Временный сбой не сбрасывает
полученную роль и формы. После исчерпания попыток показывается ошибка соединения.
Отказ роли отображается как отсутствие прав, а не истёкший вход.

Приёмка: реальный PostgreSQL-тест подтверждает, что отклонённый транспортом POST
ничего не сохраняет и последующий защищённый повтор создаёт одну запись.
Проверки доверенного/чужого прокси и подписи остаются обязательными.
Браузерные сценарии: сбой входа → успешный повтор; сбой GET в админке → доступ
сохранён; исчерпание повторов сохраняет форму; прочие ошибки записи не повторяются;
401/403 действительно убирают административный доступ. Затем саморевью и повтор
проверки в Telegram на телефоне. Стабильность сервиса туннеля этим не гарантируется.

### Реализация, проверки и саморевью

Сервер возвращает отдельный 503/code для неподтверждённого HTTPS до выполнения
операции. Клиент повторяет только этот отказ, максимум четыре попытки с
отменяемой задержкой. Сетевые ошибки, прочие 503 и 500 не повторяются автоматически.
401 сбрасывает вход, 403 отдельно сообщает отсутствие прав. Временный отказ
сохраняет известную роль и форму, включая сбой повторной проверки входа.

В отдельном проходе саморевью найден второй путь потери роли: catch в хуке
авторизации сбрасывал пользователя при любом отказе. Исправлено: сброс только
при 401/403. Добавлена проверка повторного window load с транспортным отказом.
Также защищён разбор JSON null от прокси. Повторное саморевью проверило границу
повтора до бизнес-операции, отмену и отсутствие повторов неопределённой записи.

Все 55 серверных тестов — PASS в отдельном PostgreSQL 18. Шесть браузерных наборов
пройдены; новый auth-transport проверяет повтор входа и GET, единственную запись,
сохранение формы/роли после исчерпания повторов, отсутствие повторов других
ошибок записи и корректный отказ роли. Установлена отдельная публикация с
сохранённой БД и новым frontend. Настоящий телефон после обновления ещё требует
приёмки; работоспособность ноутбука и нестабильный телефон подтверждены владельцем
для предыдущей версии. Подробности — в [verification.md](verification.md).
