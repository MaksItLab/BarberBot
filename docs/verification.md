### Вход в админку после подключения туннеля

В интерфейсе вход — «Управление магазином» сверху; он отображается только после
успешного Telegram-входа с ролью Admin. Пользователь подтвердил работу магазина,
но настоящий административный вход пока не подтверждён.

При расследовании отказа обнаружено, что первоначальный SSH-туннель не добавлял
HTTPS-заголовки. Краткий диагностический listener вернул только признаки схемы,
количество/формат заведомо неверного Authorization и факт loopback; настоящие
данные входа, адреса пользователей и cookies не записывались. Приложение
восстанавливалось в finally, PostgreSQL не останавливался.

Туннель пересоздан с явным `-- --inject-http-proxy-headers --output json`:
`https://8670437e654399.lhr.life/`. В диагностике получен X-Forwarded-Proto=https,
новый URL сохранён, старый SSH остановлен по проверенным PID и времени старта.
Каталог/readiness доступны; заведомо неверная строка входа отвергается с 401.
В последней серии два запроса дошли до проверки подписи, один не прошёл проверку
HTTPS. Значит, стабильность протокольных заголовков сервиса пока не доказана;
успешный реальный Telegram-вход не объявляется проверенным. Дополнительная
браузерная протокольная проверка завершилась тайм-аутом, без положительного
результата. Проверка HTTPS, доверенного прокси и роли остаётся включённой.

Пользователь сообщил «no tunnel» по новой кнопке и отсутствие каталога по старым.
Проверено: локальная readiness — ready, SSH PID/время старта прежние, но его
следующий JSON event register.accepted уже содержит `a899c8ad5ad946.lhr.life`.
Прежний публичный health возвращает 502, новый — 200. Это подтверждает смену
адреса в рамках одного сеанса. Текущая ссылка обновлена и приложение перезапущено
без изменения БД; настоящий административный вход остаётся непроверенным.
Предложен ngrok с закреплённым dev domain после согласия/создания аккаунта;
его установка и публикация приложения через него не выполнялись.

## Остались на localhost.run: сопровождение и вход

Владелец выбрал localhost.run; ngrok не используется. Текущий адрес динамический,
его нужно читать в `artifacts/local-tunnel/state.json`, а не из старых записей выше.
Текущий Node-supervisor поддерживает SSH с proxy headers и обновляет отдельные
appsettings.Tunnel.json только после JSON readiness=ready. Бот читает URL через
IOptionsMonitor при каждом /start. Токен/роль не берутся из временного файла.

- Все 54 серверных теста — PASS, пропущенных нет; отдельный новый PostgreSQL 18
  остановлен после проверки. Включены Production HTTPS/прокси, роли, подписи и
  фактический reload JSON-файла с сохранением токена/Enabled, смена URL между /start.
- Три Node-проверки — PASS: только регистрационные события разрешённых доменов,
  JSON readiness вместо SPA/ошибки, сохранение прежнего URL при отказе и ротация.
  Саморевью выявило необработанный JSON null; исправлено и повторно проверено.
- Штатная остановка завершила дочерний SSH; API сохранил PID и readiness=ready.
  Повторный запуск записал новый URL без перезапуска API и БД.
- При переходе на публикацию с hot reload пустая переменная окружения перекрыла
  URL и безопасно заблокировала старт. Переменная удалена, приложение восстановлено.
  После отдельной блокировки файлов Windows использована отдельная публикация;
  неизвестные процессы не завершались. Рабочий путь — в local-preview.json.
- Диагностика отказа HTTPS записывает только булевы признаки соединения,
  без заголовка Authorization, initData, токена и адресов пользователей.
  На текущем туннеле заведомо неверный запрос доходил до проверки подписи и
  возвращал 401; успешным входом это не считается.
- Frontend проверен пятью браузерными наборами: catalog, auth, admin-references,
  admin-products и auth-without-sdk. Последний блокирует внешний SDK, проверяет
  исходный launch fragment в Authorization, навигацию в админку, отказ сервера,
  повтор входа и отсутствие авторизации обычного браузера. Все API в этих наборах
  подменены; launch data тестовые, настоящий токен не используется.
- Резервный источник tgWebAppData проверен по официальному telegram-web-app.js:
  используются исходные подписанные данные, только в памяти, без разбора роли

Владелец сообщил «каталог есть, кнопки админки нет» до последнего обновления

## Телефон: транспортный отказ больше не сбрасывает администратора

Владелец подтвердил кнопку на ноутбуке; на телефоне — повторные отказы входа,
иногда появляющаяся кнопка и потеря доступа после перехода. Журнал содержит
HTTPS check failed с Loopback=True, Forwarded=False, Original=True: доверенный
прокси обработан, но итоговый протокол не HTTPS. Старый 401 ошибочно трактовался
клиентом как истечение входа, хотя запрос отклонялся до проверки подписи/роли.

- Безопасность сохранена: такой запрос не выполняет защищённую операцию, получает
  503 и secure_transport_unavailable. Неверная подпись по HTTPS — 401, запрет роли — 403.
- Все 55 серверных тестов PASS в новом отдельном PostgreSQL 18, пропущенных нет;
  кластер остановлен. В новом тесте отклонённый POST оставляет 0 брендов, повтор
  через доверенный HTTPS создаёт 1, неверная подпись ничего не добавляет.
  Прежний тест PlainHttp обновлён под новый статус отказа, без разрешения HTTP.
- Шесть браузерных наборов PASS: catalog, auth, auth-without-sdk,
  admin-references, admin-products, auth-transport. Последний проверяет четыре
  попытки максимум только при транспортном маркере, вход после сбоя, чтение
  админских данных, одну фактическую запись, сохранение полей и роли после отказа,
  отсутствие повторов при неизвестных 503/500 и сетевой ошибке, настоящий 403.
- Саморевью нашло сброс пользователя в catch повторной проверки входа. Исправлено
  и проверено отдельным сценарием window load → транспортный отказ → та же роль/форма.
  Разбор JSON null также проверен. Повторный просмотр существенных замечаний не дал.
- Release-сборка frontend успешна; установлены backend и frontend в отдельной
  публикации `artifacts/mvp-publish-transport`. PostgreSQL/данные/роли сохранены.
  Сопровождение localhost.run перезапущено на новый путь; текущий URL — в state.json.

Проверка телефона после установки ещё не выполнена. Браузерные API здесь
подменены и не заменяют реальную приёмку. Реальные подписанные данные администратора
через автоматическую проверку внешнего туннеля не отправлялись.

Дополнительная диагностика 15 октября: пользователь подтвердил общий Wi-Fi и
одинаковый VPN на телефоне и ноутбуке. Четыре последовательных внешних POST с
HTTP/1.1, чередованием Windows/Android User-Agent и заведомо неверной авторизацией
все получили 503 проверки транспорта. В предыдущей серии встречались 401, но
запрошенный HTTP/2 фактически согласовывался как HTTP/1.1; зависимость от версии
протокола или User-Agent не доказана. Проверка корневой страницы не обнаружила
Alt-Svc. Сбой воспроизводится без настоящих данных Telegram и не ограничен
телефоном. Стабильность внешнего туннеля остаётся нерешённой; права и требование
HTTPS не ослаблены.
