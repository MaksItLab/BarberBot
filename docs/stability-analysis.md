# Анализ группы стабилизации: R03–R07, U02, U03

Дата: 22.10.2026. Автор анализа: Claude, ревью: Codex, решение: Максим.
По [AGENTS.md](../AGENTS.md) анализ всей группы завершается до реализации любой
её задачи. Код в этом PR не меняется.

## Исходное состояние кода

- **Вход.** `useTelegramUser` отправляет `POST /api/auth/telegram` при запуске и
  на событие `load`. Каждый защищённый запрос заново проверяет подпись initData,
  срок `auth_date` (по умолчанию 1 час, `Telegram:InitDataMaxAgeSeconds`) и роль
  из БД. Серверной сессии нет. Поздний ответ отменённого запроса отбрасывается
  через `AbortController`.
- **Сохранение товара.** `AdminProducts.SaveAsync` записывает товар и варианты в
  одной транзакции. Правка защищена версией `xmin`, а конфликт возвращает 409 с
  советом скопировать изменения. Ключа операции нет: если ответ на `POST` потерян,
  повтор создаёт второй товар, а повтор `PUT` получает 409, хотя изменение
  на самом деле прошло.
- **Клиент.** После R01 обрыв без ответа сервера отделён от отказа, но выяснить
  исход нечем: интерфейс только советует «обновить список и проверить».
  Повторяется автоматически только `secure_transport_unavailable`. Явных
  тайм-аутов на клиенте нет, кроме сетевых тайм-аутов WebView.
- **Форма.** Состояние формы хранится только в памяти React и пропадает при
  перезагрузке, закрытии Mini App или повторном входе. Ошибки сервера — одной
  строкой, без привязки к полю.

## Источники (проверены 22.10.2026)

| Источник | Что берём |

## Предлагаемые решения

### R04 · Сохранение без дублей — первым

1. Клиент создаёт `crypto.randomUUID()` при **открытии** формы и держит его, пока
   форма не сохранена. Повтор после обрыва отправляет тот же ключ. Успешное
   сохранение или явное «Создать ещё» выдаёт новый ключ. Ключ уходит в заголовке
   `Idempotency-Key`.
2. Новая таблица `save_operations`:
   - ключ (`uuid`), Telegram ID владельца, тип операции, SHA-256 отпечаток
     нормализованного тела, ID товара-результата, время создания;
   - уникальный индекс `(owner_telegram_id, key)`.
3. Строка `save_operations` вставляется **первой командой** той же транзакции,
   что и товар (с пустым ID товара, который заполняется перед фиксацией):
   - Нет ни товара, ни ключа, либо оба есть — промежуточного состояния нет.
   - Параллельный второй запрос с тем же ключом ждёт на уникальном индексе. После
     фиксации первого он получает нарушение уникальности, перечитывает операцию
     и возвращает её результат. Отдельная блокировка не нужна.
4. Повтор с тем же ключом:
   - тело совпадает — 200/201 с актуальным состоянием товара и заголовком
     `Idempotent-Replayed: true`;
   - тело другое — 422 `idempotency_key_reused`;
   - чужой ключ не виден, потому что поиск идёт по паре владелец + ключ.
5. Узнать исход: `GET /api/admin/operations/{key}` возвращает 200 со ссылкой на
   товар или 404 «не выполнялась», и только владельцу. Это нужно U02, чтобы
   проверить исход без повторной записи.
6. Срок хранения — 7 дней (черновик R06 живёт столько же). Удаление старых
   записей — фоновой задачей раз в сутки. Срок публикуется в `docs/diagnostics.md`.
7. Объём:
   - первый шаг — создание и правка товара (`POST`, `PUT`): для `PUT` ключ
     убирает ложный 409 после потерянного ответа;
   - справочники второй очередью: у них уникальное имя, и повтор уже даёт 409
     «уже существует», это не дубль, а только неудобство.
   - Ключ на запросах товара обязателен (400 без него). Сейчас интерфейс
     единственный клиент, поэтому обратная совместимость не нужна.
8. Проверки:
   - обрыв после фиксации → повтор → ровно один товар;
   - два одновременных запроса с одним ключом → один товар, оба ответа одинаковы;
   - другой админ с тем же ключом → своя отдельная операция, не чужой результат;
   - тот же ключ с другим телом → 422;
   - `PUT`-повтор после фиксации → 200, а не 409.

### R05 · Ограниченные ожидания и повторы — после R04

- **Клиент**, общий предел на всю операцию через `AbortSignal.any` с тайм-аутом:
  - чтение — 15 с;
  - вход — 15 с;
  - запись — 30 с.
  Уход с экрана отменяет запрос (это уже есть). Отмена на клиенте не означает
  отката, поэтому запись после тайм-аута переходит в «уточняем результат» (U02).
- **Повторы чтения:** до 2 повторов при сетевой ошибке, 502, 503 и 504; задержки
  0,5 и 1,5 с с разбросом ±30 %. Учитывается `Retry-After`, если он есть и не
  длиннее 10 с. 401, 403 и другие 4xx не повторяются.
- **Повторы записи:** только с тем же `Idempotency-Key`, то есть после R04. Один
  автоматический повтор при сетевой ошибке и 502–504, дальше — U02 «уточняем».
  Существующий повтор `secure_transport_unavailable` остаётся.
- **Сервер:** `CommandTimeout` Npgsql — 10 с вместо 30 (при реализации уменьшено с 15: чтение
  с повтором должно уложиться в 15 с клиента). `EnableRetryOnFailure` не включаем (S05).

### U02 · Понятный результат сохранения — вместе с R04/R05

Кнопка и статус формы проходят состояния:
- `editing`;
- `saving` («Сохраняем…», повторное нажатие заблокировано — уже есть);
- `saved` («Сохранено», только после ответа 2xx);
- `failed` (сервер ответил отказом: текст и код обращения из R01, форма не очищается);
- `checking` («Уточняем результат…»): обрыв или тайм-аут записи, клиент
  спрашивает `GET /api/admin/operations/{key}`:
  - найдено → `saved` и подгрузка товара;
  - 404 → «Не сохранено, можно повторить» (повтор с тем же ключом безопасен);
  - нет связи → «Не удалось уточнить», кнопка «Проверить ещё раз» и черновик (R06).

### R07 · Целостность сохранения

- Добавить тесты на сбой **до** фиксации. Перехватчик EF бросает исключение на
  втором `SaveChanges` (после «временных» вариантов) → в БД нет ни товара, ни
  изменённых вариантов. Сбой **после** фиксации покрывает R04. Независимое
  чтение новым `DbContext` после остановки и запуска хоста видит данные.
- **Конфликт 409:** вместе с ответом возвращать текущую версию товара (поле
  `current` в ProblemDetails, только админу). Интерфейс показывает, какие поля
  изменил другой администратор, и даёт две кнопки:
  - «Применить мои изменения к новой версии» — повторное сохранение с новой версией
    и новым ключом, после явного действия;
  - «Взять актуальную версию».
  Молча ничего не затирается.
  При реализации «Применить мои изменения» стало трёхсторонним слиянием: поле, которое
  админ не трогал, получает значение коллеги; изменённое им поле остаётся, и форма
  перечисляет, чьи значения будут заменены. Кнопки называются «Перенести мои изменения
  на новую версию» и «Открыть новую версию без моих изменений».

### R06 + U03 · Черновик и удобная форма

> Реализовано 23.10.2026, проверки — в [verification.md](verification.md#r06--u03-черновик-товара-и-ошибки-у-полей--23-октября-2026).
> Уточнения при реализации: черновик пишется также сразу при отправке сохранения и при
> уходе из формы; «Закрыть форму» черновик не удаляет; сервер называет только первое
> недопустимое поле.

- **Хранилище:**
  - `Telegram.WebApp.DeviceStorage` при `isVersionAtLeast('9.0')`;
  - иначе `localStorage` в `try/catch`;
  - если недоступно и то и другое — предупреждение «Черновик не сохраняется на
    этом устройстве».
  - `CloudStorage` не берём: 4096 символов мало для описания до 12 000 символов
    и вариантов, и черновик не должен уходить с устройства.
- **Ключ:** `draft:v1:{telegramId}:{productId|new}`. `telegramId` берётся из
  ответа сервера на вход, а не из `initDataUnsafe`.
- **Значение:** поля, варианты, версия товара, `Idempotency-Key` и время.
  initData и роль не сохраняются. Срок — 7 дней.
- Запись — через 500 мс после последнего ввода.
- После подтверждённого сохранения черновик удаляется. После неизвестного исхода
  остаётся до сверки (R04/U02).
- **Смена аккаунта:** черновики другого `telegramId` не показываются. На общем
  устройстве при выходе черновик удаляется вручную кнопкой «Отбросить черновик».
- **Восстановление:** при открытии формы — «Найден несохранённый черновик от
  14:05. Восстановить / Отбросить». Автоматической отправки нет.
- **Ошибки у полей:**
  - сервер возвращает `ValidationProblem` с `errors` по путям (`name`,
    `variants[1].priceRub`);
  - клиент подсвечивает поля и переводит фокус на первую ошибку;
  - простые правила (обязательные поля, формат цены) проверяются заранее на клиенте.
- **Уход с несохранёнными изменениями:** `enableClosingConfirmation()` (6.2+),
  пока форма отличается от сохранённой; иначе — только черновик.

### R03 · Предсказуемый вход — решение требует выбора

> Реализовано 23.10.2026 по варианту A, проверки — в [verification.md](verification.md#r03-предсказуемый-вход--23-октября-2026).

Требования R03 «поздний ответ не меняет состояние» и «временная сеть не выдаётся
за отсутствие прав» уже выполнены R01 и предыдущими правками. Их нужно закрепить
тестами возврата из фона (`activated`) и повторного входа. Открытый вопрос —
жизненный цикл входа:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Оставить проверку initData на каждом запросе (рекомендуется)** | Нечего хранить и отзывать. Роль читается из БД на каждом запросе, поэтому снятие роли действует сразу. Код не меняется. | Через час после открытия Mini App сохранить нельзя, пока не откроешь приложение заново. С черновиком R06 ввод не теряется. |
| B. Короткая серверная сессия в HttpOnly-cookie после проверки initData | Можно работать дольше часа. | Новая поверхность атаки (CSRF, хранение, отзыв). Поведение cookie во встроенных WebView нужно проверять на устройствах. |
| C. Увеличить срок initData до 24 ч | Одна настройка. | Перехваченный initData дольше годен. Backlog прямо запрещает считать это решением. |

**Решение Максима, 22.10.2026: вариант A.** при `auth_expired` форма сохраняет черновик, показывает
«Вход истёк. Откройте приложение заново из Telegram», и после повторного открытия
черновик восстанавливается. К B возвращаться, если замеры R02 по журналу R01
покажут частые `auth_expired` на записи.

Проверки R03: неверная подпись, истёкший срок, нет роли, нет SDK (уже есть);
событие `activated` после сворачивания проверяет вход заново, не сбрасывая
форму; снятие роли в БД → следующий запрос 403.

## Порядок реализации

Один PR на задачу, в таком порядке:

1. **R04** — таблица, ключ, запрос исхода; клиент отправляет ключ.
2. **R05 + U02** — тайм-ауты, повторы, состояния результата. U02 опирается на R04.
3. **R07** — тесты до фиксации, конфликт 409 с текущей версией.
4. **R06 + U03** — черновик, ошибки у полей, подтверждение закрытия.
5. **R03** — тесты жизненного цикла и выбранный вариант входа.

Приёмка группы целиком — после R02 на настоящих устройствах. Автоматические
тесты с заглушкой Telegram её не заменяют.

## Риски и открытые вопросы

- `DeviceStorage` есть не во всех клиентах Telegram. Доля клиентов ниже 9.0
  неизвестна до R02, поэтому запасной `localStorage` обязателен.
- Новая таблица — это миграция. Её нужно применить на VPS (R08) отдельной
  командой `migrate`, иначе `/api/health/ready` вернёт 503. Это ожидаемое
  поведение R08, но шаг надо упомянуть в PR R04.
- Отпечаток тела считается после нормализации (`ProductRules.Validate`), чтобы
  незначимые различия (пробелы, `,` и `.` в цене) не давали ложный 422.
